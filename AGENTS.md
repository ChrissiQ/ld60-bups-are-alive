# Instructions for coding agents

Bups Are Alive is a realistic bacteria-evolution simulation and game: Godot 4.7 with GDScript for the game, and compute shaders on the GPU for the simulation (the only C++ is the family-tree store, `LineageStore`). [README.md](README.md) says how to build and run it, and [CONTRIBUTING.md](CONTRIBUTING.md) what a good change looks like. This file is what an agent needs to know about the project before changing it.

## What the project is for

It is a laboratory for watching real evolution happen: bups eat, swim toward food, divide, mutate and compete at real scales (micrometres, seconds), and the player can run it from real time up to x10,000. When goals conflict, in this order:

1. **It must be watchable and fun at speed.** The top playback speed (x10,000) is the most important performance target. Anything that adds per-step cost needs its cost measured at that speed. A little speed can be traded for clear accuracy, not a large chunk.
2. **It models real evolution accurately.** It is a realistic *life* simulator, not just an E. coli simulator: prefer the realistic mechanism over a gamey one, and say where realism was scaled for playability (mutation *rates* are raised well above a real microbe's, the *shape* of the spectrum stays realistic). A feature borrowed from another organism is fine if the combined organism is plausible and keeps the feature's real costs and trade-offs.
3. Everything else.

There are exactly **two clocks**: real time, and the simulation clock (playback speed multiplies it). Do not invent a scaled "game clock"; show times with `SimClock.format`. Units are µm and seconds. "Metabolism" is a gene, nothing else.

## Layout

- `scripts/`, `scenes/`, `ui/`: the game. `scripts/dish.gd` is the game's face of a dish (its row in the simulation, its edits sent to the simulation, picking, layers, and what it shows from the newest snapshot), `scripts/dish_drawing.gd` draws it and `scripts/dish_codec.gd` is its save format; `scripts/main.gd` is the game screen (wiring and the per-tool clicks; `ui/stage_input.gd` is its camera and pointer input, `ui/inspector.gd` and `ui/panel_text.gd` the info panel and hover card, `ui/lineage_view.gd` the lineage browser and its stack, `scripts/play_holds.gd` what holds the game; a dish's selection and hover are `Dish.selected` and `Dish.hovered`, `scripts/dish_pick.gd`); `scripts/session.gd` carries state between screens; `scripts/start_conditions.gd` is how a dish begins; `scripts/goal_tracker.gd` holds the experiments' goals.
- `scripts/sim/`: the simulation's host side (see "The simulation" below). `gpu/`: the kernels, their layouts and the shader set. `native/src/`: only `LineageStore` (the family tree of every bup, a GDExtension) and its registration. `scripts/sim_constants.gd` builds the constants the kernels receive.
- `text/strings.cfg`: every word the player reads. `text/names.txt`: random bup names.
- `tests/` and `tools/`: tests and generators. `gpu/`: the GPU path (see "The simulation" below). `tests/sim/`: the windowed (GPU) simulation tests. `.github/workflows/`: the lineage store's build and the release.

## Conventions the tests enforce

- **All player-facing text** lives in `text/strings.cfg`: `Strings.t("section.key", args)` in code, `"@section.key"` in scenes, a comment above each key. `tests/strings_test.gd` checks that every key exists and that every raw file the game reads is covered by each export preset's `include_filter` (a raw file missing from an export makes the game show keys instead of words).
- **UI styling lives in the theme** (`scenes/menu_theme.tres`). Use `theme_type_variation`; add a variation to the theme when none fits (its base type must be a plain Control type, not another variation). No per-node overrides, no styles or colours built in code (colours only in `dish.gd`, `dish_drawing.gd` and `genome.gd`), two typefaces in `fonts/` (IBM Plex Sans for text, Commit Mono for numbers; which is set only in the theme), numeric settings through `ui/setting_row.tscn`. `tests/ui_lint_test.gd` fails on any of this. Screen paths live in `scripts/scenes.gd`.
- A bup's name has one source (`bup_names.gd`); do not build names elsewhere.

## Repository conventions

- **A yes/no setting is a `ToggleRow`** (`ui/toggle_row.tscn`: its name, On and Off buttons, and what it does written below, always in view), never a bare toggle button and never explanation that only a hover shows (tooltips do not wrap and run off the screen: keep them short, for names and icons). Render a new screen (a `SubViewport` holding it, saved as an image) and look at it before calling it done.
- **Free-mode defaults are goal mode's settings.** `StartConditions.new()` holds the defaults, goal mode's dish is `dish.strike(null)`, which uses `StartConditions.new()` (`tests/free_mode_test.gd` checks the defaults), so free mode differs only in letting them be changed. A feature that is on in goal mode and a toggle in free mode is on by default there, and "reset to defaults" restores `StartConditions.new()`'s value.
- **The encyclopedia is kept true and complete, and kept to concepts.** An entry explains a term in up to two parts, kept apart as the Civilopedia keeps them: `<id>_about`, what it is in real life, and `<id>_game`, how it works in the game (values, ranges, costs, and where the game departs from real life: a rate raised, a trait standing for many genes, a number that is a game choice). It never says what to click or press, never what a control does: that is the tutorial's (`[tutorial]`, the steps in `Main._start_tutorial`) and the tooltips', which are names and icons only. Every change that alters what an entry says (a constant, a cost, a rate, how a gene or mechanism works, a name, a range) updates the entry in the same change, and a new gene, flag, mechanic, thing in the dish or term the player meets gets an entry (`scripts/encyclopedia.gd`, `[encyclopedia]` in `text/strings.cfg`); a changed or new interface part updates or adds a tutorial step. Check the game part against the code, not from memory. Anything about real biology is looked up and checked against sources before it is written: no misconception may stand in an educational text. `tests/encyclopedia_test.gd` checks the links, that every gene has an entry and that no entry tells the player what to click; it cannot check the facts.
- **Committed files are written for any reader.** Comments are for future developers and documentation for future audiences: nothing tracked speaks of one person, one person's computer (its programs, displays, sizes or set-up), one session or one agent. Nothing tracked cites a file that is not tracked, a plan or its labels (a package, a phase, a numbered row or decision), who decided something or when, a conversation, or the work's own history: a reader with only the repository must be able to follow every sentence. Say the general condition ("a window manager may resize a new window"), and name a set-up only in the generic sense and only where the reader needs it (what a figure was measured on: "Apple Silicon, Metal"). Notes about a particular machine, run or person go in files that are not tracked. Read a diff for such wording before committing it.
- **Commit messages** are one short line in the present tense, third person ("Fixes source selection"), with no body and no attribution trailer.
- **Secrets:** do not create, edit or delete `.env` files; reference their variables.
- **Saves are not stable.** The game is unreleased, so do not write code that reads old save formats, and do not edit a real `save.json` or `free_settings.json` in the user data folder; tests use scratch paths.
- **Releases** are made by pushing a `v*` tag (see CONTRIBUTING.md); changing a workflow in `.github/workflows/` changes what builds.

## Interface design

The look and layout are one system. The theme (`scenes/menu_theme.tres`) is **generated** by `tools/gen_theme.py` from design tokens, which live only in `design/tokens.json` (W3C Design Tokens format, read by `tools/design_tokens.py`; colours, fonts and weights, sizes, radii, spacing; sizes are px; the page documents the game and says nothing of CSS, and its own text is plain web styling, not the design system; any text in the design page's examples is the game's own wording from `text/strings.cfg`, never invented; a colour, size or gap written as a number in a generator fails `tests/design_tokens_test.gd`): edit the tokens there (or a variation in `gen_theme.py`), run `python3 tools/gen_theme.py` and `python3 tools/gen_design.py` (which writes the design system page `docs/design-system.html`) from the project root, then `godot --headless --path . --import`; never edit the `.tres` or the `.html` by hand. `tests/design_tokens_test.gd` fails when either is stale. The page reads the interface-size constants (`SCALE_MIN`, `SCALE_MAX`, `ROOM_EXPONENT`, `PLEX_SIZE`, `MONO_SIZE`) from `scripts/user_settings.gd` and each font family's `body_height` from the tokens (measured from the font file), and checks text against the Xbox Accessibility Guidelines 101 and 102, which are written for games. Layouts are containers, never hand-placed offsets.

- **Tokens, type, spacing, radii and components** are documented in `docs/design-system.html`, the source of truth for the design system. Do not restate them here or in comments; change `design/tokens.json` or `tools/gen_design.py` and regenerate.
- **Keep the design system current.** Any change to the interface that touches the design system (a colour, font, size, radius, spacing, component, layout rule or behaviour) ends with a review of `design/tokens.json`, `tools/gen_design.py` and the page, across every area, not only the part you changed. A token no longer used is removed. A token whose purpose changed is renamed if its name is no longer accurate (names are roles, never appearances), with its description and the page's text updated. A new need reuses an existing token before adding one. Text on the page must describe the game as it is now, with no trace of an earlier choice. Regenerate, and run `design_tokens_test` and `ui_lint_test`.
- **Controls:** a yes/no setting is a `ToggleRow` (segmented On / Off; with `auto_text` a checkbox that dims the switch while the machine decides). Pages of one panel are tabs (`TabButton` in `Segments`); steps of a flow are a `StepIndicator`; a section that hides detail is a header button with a chevron (`SectionButton`); numbers are `SettingRow`; a secondary action is `SmallButton`, a real raised button (never a borderless "ghost" button or a bare text link: an action always looks like a button; Reset sits at the left of the footer, Back / Next at the right). Keys are shown in tooltips and the controls list, never in a button's or hint's text. A warning is the coral icon (`WarningIcon`) and text (`Warning`) together. Do not use a toolbar button for a setting, and do not make something that is not a control look like one.
- **Dialogs** (`scripts/dialog_style.gd`): the look is in the design system page (Floating surfaces).
- **In-game screen:** `HUD/Frame/Layout`: the top bar (readout, dish tabs that scroll (each with a small live picture of its dish), layer toggles, playback, menu), then the middle (tool rail and stage; the right-hand tray). The dish is framed in `%Stage` (`StageInput.fit_camera`, again whenever the stage resizes). **Everything that is a panel lives in the tray**, which scrolls when short: the goal, the card of what is picked (a bup, a source, a plankton: only while something is), then accordion sections, all alike (collapsible, draggable, never hidden by a pick): the **Dish** (its bloom and feed rates, Freeze and Trash), its **Dish details** (`TraySection`, `ui/tray_section.gd`: a `SectionButton` heading with a chevron at its right, content under it, put as the node's children in the scene; the panel (`TraySectionPanel`) has no vertical margin: the heading brings its own room above and below and the content (`SectionBody`) its own below, so an open section is not padded twice): **Graph** (Y opens and closes it; a dish switch when there are several dishes, the time span switch, the trait drop-down, the plot), **All dish details** (the dishes running, the bups in all of them and the traits averaged over every bup of every dish), the watch list, and the **Freezer**. Add a new panel as a plain `TraySection` node of `scenes/main.tscn` (script `ui/tray_section.gd`, no scene or subclass of its own, no size flag or `reset_size` of its own) with its content as children; logic that fills the content goes in a content component the section holds (as `WatchList` is for the Watching section). A panel that is its own scene or a subclass is how one section ended up unlike the others (it could not collapse, did not shrink, and had its own width), and `tests/tray_sections_test.gd` fails on any section that is not the same as the rest: same script, same flags and theme, the same width as the others in every state, and only its heading when collapsed. Sections are reordered by dragging their headings (`TraySection` `_drag_data`/`_can_drop`: the heading lifts the section out, a `DropSlot` "Move here" (`ui/drop_slot.gd`, theme type `DropSlot`) marks where it lands and follows the pointer, Esc or a release outside the tray puts it back, saved on drop as `UserSettings.tray_order` in preferences, a global setting; `apply_order`; "Use defaults" clears it). What the pointer rests on is the hover card by the pointer and never moves the tray. `_adapt_layout` sizes the tray and the graph; no top-bar control is ever hidden: when the layer toggles do not fit beside the rest of the bar's row (the dish tabs having shrunk to two tabs and their arrows first) the tabs and the toggles move to a second row (`_fit_top_bar`: the speed text (`SpeedReadout`, "x10,000", and "x10,000 (x3,400)" with what is reached when that is under 85% of it; pause shows only in the ring and the lit buttons) leaves the readout for the row's left, the tabs sit between it and the toggles, centred in the free space when they fit and against the toggles when not, the toggles at the right; the speed label reserves the width of its longest text, so nothing moves when the speed changes and the tabs move only when the number of dishes does; that width is measured again when the label's own theme font size changes, never keyed on `UserSettings.text_factor()`, because `apply()` fires `size_changed` before the theme's fonts are rescaled), and the tabs shrink (arrows reach the rest) down to the arrows and a sliver of a tab if the window leaves nothing else (`tests/top_bar_test.gd`). Every layout-only container has `mouse_filter` ignore or it swallows clicks meant for the dish.
- **The encyclopedia and tooltips:** what the game's terms mean lives in the encyclopedia (`scripts/encyclopedia.gd` for the order, `[encyclopedia]` in `text/strings.cfg` for every word, `ui/encyclopedia_panel.gd`), reached from the title screen and the pause menu, and opened on an entry by a click on a band of the genome map (`Main._open_encyclopedia`); an article links to another with `[url=id]words[/url]`, and `tests/encyclopedia_test.gd` checks every link. A new term gets an entry, not a long tooltip (tooltips are names and icons only), and the `TooltipFit` autoload wraps every tooltip to `UiText.TOOLTIP_WIDTH` characters a line as the pointer reaches its control.
- **The freezer:** a dish is frozen with the Freezer section's button ("Freeze this dish": the one in the main view) or by answering a pipette's question (`_ask_about_old_dish`: after the pipette makes its new dish the game holds and a dialog asks Keep, Freeze or Trash for the dish the bups came from; only a button answers; play, which the pipette timer was holding, goes on after). `Main.freeze_dish` keeps the dish's shown number, its host part (`Dish.host_part()`), its bup count and its picture, and asks the simulation for the dish (`Dish.freeze()`: a `SimReply` holding a `DishBlob`, whose lineage is `host["lineage"]`), then frees the dish (`_remove_dish`): a frozen dish is in no running list and has no row in the pool, so it is outside the world's clock and the all-dishes graph, and does not advance. `Main.thaw` makes a new `Dish` from the blob (`Dish.load_blob`, a new world row; `_register_dish` gives it the old shown number) and pads its history up to the world's time (`DishHistory.pad`); a thaw the pool has no room for (row below 0) shows the `banner.memory_budget` banner. `trash_dish` removes a dish for good. The last running dish can be neither frozen nor trashed; at `MAX_DISHES` (999, the interface's three digits; the world's own limit is `GpuLayout.D_MAX` rows) running a dish cannot be thawed (frozen ones do not count). When the last running dish dies out with dishes frozen the game does not end: it stays, empty, until one is unfrozen. The Freezer section lists the frozen dishes (`ui/freezer_shelf.gd`: a row each with its picture, "Dish N: M bups" and Unfreeze, Info and Trash icon buttons; Info opens a details line under the row, since a frozen dish is saved data, not a live `Dish` the dish card could show; Trash asks first). The freezer is not saved with a game (several dishes are not either). `tests/freezer_test.gd`.
- **The bup's panel** (pinned: name row, then `BupGauges`, then born, divisions, steering, dish, the genome map, mutations, harm; the hover card has the same under its text): MASS and RESERVE are two bars (`ui/gauge_bar.gd`, `ui/bup_gauges.gd`). The mass bar's length is the body's (mass drawn as a length): a white tick at the birth mass, the end where it divides (`div_mass`: birth mass plus what its size gene adds, from the simulation), with starvation on a red tick at the death mass; its number is the mass. The reserve bar's track is the most the body can hold, its fill the energy, a tick and a muted band at `Cell.MAINTENANCE_FLOOR`; its fill and word are amber while it sits at the floor and the bup still grows (food-limited), red when starving (mass below birth mass with starvation on, or far below the floor without), green otherwise; amber is also this reserve state, besides goals and names. A dead bup's bars are what they were when it died, in grey: the record keeps `mass`, `energy` and `birth_mass` (taken by `record_death`, and carried by the GPU's death events, which are 14 words, words 8 and 9 the energy and the birth mass, 10-13 the genes; the layout is `gpu/gpu_layout.gd`'s `ED_*`). The divisions number shows in the flash colour for `FLASH_MSEC` after the bup divides (`UiText.numbers(text, "divisions")`, theme type `BrightFlash`).
- **The genome map:** a bup's genes are shown as a chromosome (`ui/genome_ribbon.gd`, `ui/genome_slot.gd`), the way a graphical genotype colours one: a bup is haploid with one chromosome, so the loci are bands down one bar in the fixed order `Genome.LOCI` (the donor's F factor, then speed, sense, metabolism, size in the order a donor transfers them, then the mutator and the acetate key), each band its locus's colour (`Genome.LOCUS_COLORS`) with the gene's symbol in it, its shade the allele (dim to bright across the gene's range), the value beside it. A bup without the F factor has an empty band there. A dead bup's family record keeps every gene (the F factor and the reach word too: the record takes them at birth, and a GPU birth event carries them in the upper bits of its mutations word; the genes and the reach word again at death, as a conjugation may have changed them, from the death event), so its map is the one it had in life. A new gene or flag goes in `Genome.LOCI`, the ribbon's `show_bup`, and the `[genome]` strings.
- Bups are artwork, not interface: accessibility work is for the interface (contrast, reduced motion, sizes); never alter bup colours or behaviour for it.
- Look at a screen at 100%, 150% and 250% in a busy state (several dishes, a picked bup, a full watch list, a tool open) before calling it done, and run the full interface suite as tracked tasks (a script error leaves a headless test hanging until its timeout).

## Interface size

How the interface scales is in the design system page (Interface size). Consequences for layout: never place a panel at a fixed pixel offset that a bigger font can overrun (use containers, a title's measured bottom, a ScrollContainer as the fallback), and look at a screen at 100%, 150% and 250% before calling it done (a capture script can set `UserSettings.native_override` and `ui_scale`, then `apply()`). Headless runs are given a 1280 x 720 window and ignore the saved preferences.

## Debug log

F12, on any screen (undocumented in the game: not on the HUD or in the controls; only its notice is in `strings.cfg`), writes `bups-<date>_<time>-<ms>.log` and a `.png` of the screen to `user://logs/` (on macOS `~/Library/Application Support/Godot/app_userdata/<project>/logs/`), then shows "Debug info logged" for a few seconds. The log is JSON: the run's settings and state, the mean nutrient by distance from the dish centre (a rim ring or step shows there), the selected bup, and every simulation constant. It works in menus and in the tutorial: the `DebugHotkey` autoload (`ui/debug_hotkey.tscn`) takes the key, logs the current screen and the session, and the screen's `dish` and `debug_state()` when it has them. Each write prunes the folder to the newest 20 logs and nothing older than 14 days. When diagnosing a report, read the newest log (`ls -t`) and its screenshot. `scripts/debug_log.gd` builds it; add to `report` what a diagnosis keeps needing, and keep personal data out.

## The simulation

The simulation is one pooled world on the GPU: every running dish's bups, nutrient grid, clouds and husks share one set of buffers, and a dish's run does not depend on what else is in the pool. There is no CPU simulation, no backend setting and no Auto rule: a machine that cannot make a local `RenderingDevice` with the imported `pool_*` shaders gets `CpuSimBackend`, a stub that runs nothing (`can_simulate()` false, commands dropped, an empty snapshot), which is also what a headless run has. The model lives in the kernels and nowhere else.

- **Threads and the seam:** `SimService` (autoload, `scripts/sim/sim_service.gd`) makes the backend once (`GpuSimBackend` when `available()`, else the stub). The main thread talks to it only through `WorldClient` (`scripts/sim/world_client.gd`, reached by `WorldClient.shared()`): commands (`add_dish`, `remove_dish`, `freeze`, `thaw`, `pipette`, `resize`, `set_params`, `edit_world`, `set_time`, `set_view`, `ask`, `inspect`, `save_all`...) go in a queue, answers come back as a `SimReply`, and what the world looks like is the newest `Snapshot` (`latest()`, `snapshot_changed`). `WorldClient` hands out the lowest free client row for a dish. `SimBackend` is the seam; `tests/fakes` holds the test double. The sim thread (`SimThread`) owns a local `RenderingDevice`, a `SimCore` and a `DishWorld` per dish, and loops: drain the commands, ask the `Governor` for steps, run an iteration (record, submit, sync), copy out the dish state, stats and family events, hand them to `ResultWorker`, publish the main dish's pictures. `ResultWorker` (a second thread) applies the family events to `LineageStore`, decodes the stats and builds the `Snapshot` it swaps in under a mutex. An iteration the memory budget refuses puts the dishes' worlds back and is retried with fewer steps.
- **The pool:** `SimCore` (`scripts/sim/sim_core.gd`) is synchronous and threadless. A dish takes a row of the `DISHP`/`DSTATE` tables (`GpuLayout.D_MAX`, 1024), a 256-aligned segment of record slots, a 256-aligned block of field cells and its cloud-list squares. `SimArena` holds the buffers by unit class and grows a class by 1.5 when a batch would pass 90% of a buffer; it shrinks a class that used under a quarter of its slots for a minute, never below room for the most it was asked for in that time (`asked`: room made ahead for a step's worst case is not shrunk and grown back); the cloud lists' entries (`ENT`, `ENTD`, 36 B an entry) are a class of their own, starting at 12 a cloud slot and grown from the entries a cloud was measured to take (the room kernel leaves the peak and the density in `WD_ENTRIES_PEAK` and `WD_ENTRY_DENSITY`; `SimArena.ensure_entries`, with `SimCore.ENTRY_MARGIN` 1.25 of room), since a cloud that reaches several squares takes 25-56 entries, the kernels cut a dish's lists at the real capacity (`WD_ENTRY_CAPACITY`) and at `ENTRIES_PER_CLOUD_MOST` (256) a cloud of its quota, and a cut still raises the overflow flag; `PoolLimits` has the starting sizes and the memory budget: `MachineMemory` (`scripts/sim/machine_memory.gd`) is the one meaning of the machine's physical and free memory on every platform (the engine's own figures differ by system), `PoolLimits.budget_for` gives the ceiling from it (0.4 of the physical memory, 1 to 8 GiB; 2 GiB when the adapter has memory of its own or does not say, since a card's memory cannot be read), `MemoryWatch` (`scripts/sim/memory_watch.gd`) sets `memory_budget_bytes` to a working budget every 5 s and before a growth (what the pool holds plus half the free memory, between the floor and the ceiling; it falls at once and rises with hysteresis; the arena shrinks sooner while the machine is short), `PoolLimits.classify` says whether the machine has enough, is low or is below the minimum, `PoolLimits.new()` keeps a fixed 6 GiB for tests, and `tools/gpu/mem_check.gd` is a probe of all this for any machine. The player's side of it: `MemoryMode` (`scripts/memory_mode.gd`) says whether the game is in low-memory mode (the machine is low or below the minimum, the Options setting says Low, or a custom ceiling is under 2 GB) and gives the limits that mode puts on a dish (`PoolLimits.LOW_BUPS` 500,000 bups, `LOW_DISHES` 10 running dishes, `LOW_GRID` 200 cells across; a loaded or thawed dish over one runs as it is and cannot be raised); the Options row (`ui/memory_row.tscn`: Auto, Low, or Custom with a number of GB; `UserSettings.memory_mode` and `memory_gb`) reaches the simulation through `WorldClient.set_memory`; a notice after the start says when the machine is below the minimum or the mode is on (`MemoryNoticeDialog` in `scenes/main.tscn`, once a run for each text, after the tutorial); a refused growth shows `banner.memory_budget`; the encyclopedia's memory entry explains it, and its numbers are the code's; `PoolLimits.warning_state` is the 90% warning the game shows as a banner. `DishWorld` (`scripts/sim/dish_world.gd`) is a dish's plankton, bloom, sources and emitters on the host: its events (clouds, deposits, husks) are stamped with the step they belong to, and `checkpoint`/`restore` undo a refused window.
- **Time:** every dish shares one world clock: `Main._advance_world` sends `WorldClient.set_time(sim_speed, paused, real_dt)`. The `Governor` (`scripts/sim/governor.gd`) turns it into steps: a step is `min(MAX_STEP, speed / STEPS_PER_SECOND)` (20 s, 120 a second), an iteration takes as many owed steps as fit `T_ITER_MS` at the measured cost of a step (the starting estimate, 25 ms, until a step is measured; not tuned) and `MAX_STEPS` (`GpuLayout.MAX_STEPS_PER_BATCH`), owed time is capped, and a duty cycle backs off when frames run long. Below `MAX_STEP` a display frame owes one frame's worth of steps (`frame_steps`) and every iteration publishes one picture: after a late iteration the catch-up runs a frame's worth at a time, each with its own publish, while the sim keeps up on its slow mean (`keeping_up`) and at most `SPLIT_OWED_MOST` frames' worth are owed; past that the owed steps merge into one iteration. With nothing owed the sim thread waits for the next command; at one step a frame, with iterations that fill at least `SPIN_SHARE` (half) of the display's frame, it spins in place of that block (`SimThread._wait_for_tick`, for at most two frames after the last `set_time`), because a thread that slept runs the next iteration's GPU wait slower (a one-step sync of about 4.3 ms against 3.0 at 100,000 bups) and the picture then misses its frame; the spinning replaces sleep-and-wake time, so the process uses about half a core either way (0.51 spinning against 0.47-0.53 sleeping). If the machine cannot keep up the whole world slows together (`achieved_speed`).
- **Dishes in the game:** `main.gd` keeps `dishes` (every running `Dish`, children of Main) and `dish`, the one in the main view; `add_dish(start)` joins one, `set_main_dish(d)` brings it into view (graph, watch list, layers, camera follow; a selection or lineage open on the old one is closed). `Dish.number` is the world's number and is never reused; the number shown (`_take_label`, 1 to 999, then the lowest free among running and frozen dishes) is a label that a thaw keeps. `ui/dish_strip.gd` (`DishStrip`) shows each running dish's tile of the thumbnails' atlas (`ThumbAtlas`, `DishThumb`, written once a second by the simulation) and is hidden with one dish. The dishes not in view keep their history from the snapshots they are handed: each holds at most `Dish.BACKLOG_MAX` samples waiting to be recorded (thinned between the oldest and the newest when more arrive, the gaps filled when they are taken, so its graph keeps its time span), and `Main._record_parked_history` records them inside a time allowance each frame. A dish that dies out pauses the game on it (`_on_dish_extinct`); resuming deletes it (`_retire_extinct`) unless it is the last running one; the last running dish dying out ends the game (`_game_over`, `EndDialog`) when the freezer is empty, and otherwise leaves it empty until a dish is unfrozen. Goal mode stays single (the pipette is locked there). `tests/dishes_test.gd`, `tools/gpu/dishes_check.gd`, `tools/gpu/dishes_perf.gd`.
- **Pipette:** `Dish.pipette(world_pos, radius)` asks the simulation for a retarget (a zero-step iteration that moves the bups in the circle to a new row, same ids; `SimCore.pipette`, kernels `pool_pip_*`; the new dish's grid is made ahead on the worker pool), the waiting pipette keeps its source dish's number and is refused if that dish has left its row by the time the grid is ready (a freed row is given out again at once; `tests/sim/pipette_row_reuse_test.gd`), and `Main._finish_pipette` adopts the new `Dish` (`adopt`) and then asks Keep, Freeze or Trash about the old one (`_ask_about_old_dish`). The family tree stays in `LineageStore` under the same ids. The watch list is one for all dishes (`WatchList.dishes`), what the layer buttons show is one choice for every dish, each dish keeps the zoom and position the camera had when it was last looked at (`Dish.view_zoom`), and with the timer on (`tool_options.pipette_timer_changed`) the game pauses every so many simulated hours until a pipette moves bups (`Toolbar.resume_locked`).
- **Husks:** `Dish.plankton_husks` and `Dish.death_husks` (`StartConditions`, advanced options, off by default) make a dying plankton or bup leave a husk instead of a cloud (`pool_husk_*` kernels, a husk buffer in the pool, `Biology.HUSK_SECONDS`). Husks have a layer of their own (`Layer.HUSKS`, default key M) and a mode of the select tool, both there only while the dish in view can have husks (`Dish.has_husks`; `LayersPanel.sync_from`, `ToolOptions.set_husks_available`). Every husk is drawn; what can be pointed at is what is drawn. The select tool's Husks mode (and Inspect all) finds one by its place (`SimCore.husk_near`, `Dish.husk_at`, `husk_details`; a husk has no id), with a hover card, a pinned panel and a ring.
- **Views:** the simulation writes shared textures (the bups' payload, ids, haze, steer, thumbnails: `SimCore.publish`) and the main device imports them (`ViewRenderer`, `scripts/sim/view_renderer.gd`), runs the `view_*` kernels, draws the bups into a MultiMesh and answers picks. The display shows the oldest publish it has not shown and keeps at most `WorldClient.WAITING_MOST` (2) waiting; `SimCore.TEXTURES` (10) is the ring of shared textures of each kind, which must hold `WAITING_MOST` + 6 publishes at one publish a frame. A bup shorter on screen than `Cell.MIN_VISIBLE_LENGTH_PX` is not a capsule: those bups are one picture in which each texel takes the colour of one bup that covers it (the winner, never a mean, so a crowd keeps the bups' own colours), built by the `view_*` density kernels (`ViewRenderer.set_density`, turned on by `DishDrawing._ensure_view`) and shown by `DishDrawing.density_sprite` under the capsules, only once it has been built for the dish in view; a bup at or over that length is a capsule as before, and if the density kernels do not build every bup is a capsule (`tests/sim/winner_view_test.gd`; `tools/gpu/den_shots.gd` shoots both drawings side by side).
- **Kernels:** every kernel is GLSL text and its buffer list, written by concern with its registration (`gpu/kernels_field.gd`, `kernels_life.gd`, `kernels_clouds.gd`, `kernels_husks.gd`, `kernels_game.gd`, `kernels_draw.gd`, `kernels_core.gd` (host operations: clearing a row, edits, ids, copies into the shared textures), `kernels_view.gd`: each a `register(out)`); `gpu/kernels.gd` (`GpuKernels`) is how a kernel is made (`add`, the buffer types, the shared header and functions, the scans) and `GpuKernels.all()` gives them all; `tools/gen_gpu_shaders.gd` writes them to `gpu/shaders/<kernel>.glsl` (generated: edit the `kernels*.gd` files, never the `.glsl`); `gpu/shader_set.gd` (`ShaderSet`) loads the imported shaders, or compiles the text from `GpuKernels.all()` at run time for tools. The game runs the `pool_*` kernels (and `ev_deposits`, and `view_*` on the main device); the older single-dish kernels are still registered and generated.
- After editing a kernel (`gpu/kernels*.gd`): `godot --headless --path . -s tools/gen_gpu_shaders.gd`, then `godot --headless --path . --import` (the importer reports success even when a shader fails to compile; `tests/gpu_shaders_test.gd` reads the errors and fails on stale files).
- **A death gives back nutrient:** a bup that starves or dies by chance returns `Biology.DEATH_RELEASE` of its body (mass at `COST_PER_MASS`) as a cloud where it died (`pool_death_clouds`, `pool_death_count`); one displaced at its dish's limit (the trim) or removed by an edit returns nothing. With `death_husks` a death leaves a husk instead, and makes no cloud.
- **Starvation (stationary phase):** `Dish.stationary_phase` (`StartConditions.stationary_phase`, off by default in free mode and goal mode alike, an advanced option in free mode; goal mode's dish never has it; the `DPF_STATIONARY` flag of the dish) changes what happens to a bup whose reserve is at `MAINTENANCE_FLOOR`: it stops growing, pays `Biology.STARVE_MAINTENANCE` from its reserve and then from its mass (it shrinks), and dies at a constant rate that grows with its metabolism gene (`Biology.STARVE_DEATH_RATE`, `STARVE_DEATH_GROWTH_HOURS`) or when it has shrunk to `STARVE_MIN_MASS_SHARE` of its birth mass, instead of dying when the reserve is gone. Kernel: the end of `pool_life`.
- **Conjugation:** a bup's record word 14 is its donor flag (0 or 1; the drag cost is worked out from the speed gene). A donor (`Genome.DONOR_*`, `CONJ_*`) copies a run of its genes into a non-donor it touches: `pool_conj_clear`/`pool_conj_count`/`pool_conj_scan`/`pool_conj_scatter`/`pool_conj_apply` before `pool_life` (a hashed table of donors by 20 µm cell per dish; each recipient looks at the cells as far round it as the largest donor could touch it, and changes only itself). `tests/sim/conjugation_isolation_test.gd` checks that dishes do not touch.
- **Raised ceilings:** a bup's record word 12 is its `reach` (two bits a gene, speed the lowest: how many times that gene's ceiling has been raised, `Genome.REACH_*`), not its food yield, which is `exp(-harm) / sqrt(metabolism)` worked out where it is read. A raise multiplies the gene's `gene_max` in the mutation clamp (in `pool_life`), costs growth, and travels with the genes in a conjugation.
- **Acetate (the second food):** a bup that takes in more than its growth can use lets go of acetate besides (`Biology.ACETATE_*`: threshold-linear in the growth rate its intake could sustain, its own gain not reduced), and a bup with room in its reserve takes acetate up from the cell it is in, at up to 0.45 of its glucose rate and less while there is glucose. The acetate is a second field in the pool (the main field's grid and medium, no clouds, diffused with it; `DPF_ACETATE`): `pool_ac_cells` and `pool_ac_apply`, `pool_diffuse2_a`/`pool_diffuse2_b`, and the fused `pool_ac_conj_life`. Not modelled: inhibition by acetate (not significant at neutral pH), the glucose of clouds in the repression, a view of it in the game.
- **Acetate key:** `Genome.key_level(reach)` (bits 8-9 of the `reach` word: 0 none, 1 potentiated, 2 the key; the gene-ceiling code reads only the low eight): a division potentiates a level-0 line at `KEY_POTENTIATION_RATE`, a level-1 line makes the key at `KEY_RATE`; the key multiplies acetate uptake by `KEY_FACTOR` and costs `KEY_COST` of growth. The stats pass sums it as a ninth value (`key`, a graph series).
- **Divisions and generation:** a bup has `divisions` (record word 20), the divisions in its line: a division adds one to the parent, lethal daughter or not, and the daughter starts at the parent's new count, as both products of a fission are one step further on. A bup has no generation of its own. The population's `generation` is the mean `divisions` of the bups alive in the dish (the stats pass's tenth sum), as the LTEE counts generations per population; a pipette keeps the bups' counts, so the new dish carries on the count of its source.
- **Limits:** a dish's bups are held at `DP_LIMIT` with a hard cap `DP_CAP`; the trim expects the step's growth plus a margin of `CAP_SIGMAS` standard deviations, so the count stops a little short of the limit and is over it in a small share of frames (`tests/sim/cap_test.gd`).
- **The field pass is fused:** `pool_fdiff` (`gpu/kernels_field.gd`) does the feed and the diffusion of glucose and acetate in 16x16 shared-memory tiles with a halo of 3, in rounds of at most 3 iterations (an odd count of rounds, so the result always lands in `EFF` and `CONC2B`; the fixed `TILES` buffer, built by `SimCore._sync_tiles`, lists the tiles with the dishes that need the most rounds first). `pool_dep_land` copies `EFF` to `CONC` with the deposits added; `pool_clear` is out of the step (`pool_cells` zeroes the owner cells' sums). `pool_apply`, `pool_apply_count` and `pool_ac_cells` read the acetate from `CONC2B`, `pool_ac_cells` writes `CONC2`. The arithmetic and its order are the unfused pass's, so the goldens hold byte for byte; `SimCore.lone_field` runs the unfused path (`pool_feed`, `pool_diffuse_*`, `pool_dep_apply`, `pool_clear`, `pool_land_copy`) for `tools/gpu/fused_check.gd` and `pool_diffuse_check.gd`. Field traffic is about 74 B a cell a step at 2 iterations. Per-kernel profiles of small dispatches are unreliable here: compare paths by interleaved wall-time batches.
- **Layouts:** every word of the bup record (28 words, 112 bytes, the 64-bit id as two uint words, 0 and 21; words 24-27 are the chemotaxis memory), the family events, the `DISHP` and `DSTATE` rows, `WORLD`, and every slot of P (with its kind: `const`, from `SimConstants.build()` and set at the load; `array`; `dish`; or `batch`, set for each iteration) is named once in `gpu/gpu_layout.gd` (`GpuLayout`). `GpuKernels.add` declares the names a kernel uses at its top, so the GLSL and the host code read them, never numbers. A new record word, counter or slot goes there (a new constant in `SimConstants.build()` that the GPU reads is a "const" slot, filled by name). Move records through the integer views, never as floats (`scripts/sim/record_codec.gd` is the host's codec). `tests/sim_layout_test.gd` (headless) checks the table.
- **A dispatch runs whole workgroups.** A kernel dispatched for fewer threads than its `local_size_x` (one thread runs a group of 64 invocations) must bound its index: a single-thread kernel begins with `if (gl_GlobalInvocationID.x != 0u) return;`, the others return past their count. Without it a second SIMD group sometimes applied an update again under GPU load (doubled deposits and clouds, the step counter and next id advanced twice).
- **The main RenderingDevice** (the game's views run on it; the simulation itself runs on the sim thread's own local device): every call goes through `RenderingServer.call_on_render_thread`; never `submit()` or `sync()` (the frame submits); results come back with `buffer_get_data_async` a few frames later (the stalling `buffer_get_data` only where a stall is meant: a save); every `buffer_update` of a batch comes before its `compute_list_begin` (the device refuses updates while a compute list is open); never set `multimesh.buffer` or a per-instance setter on the GPU-drawn MultiMesh (a CPU copy would overwrite the GPU's).
- **The windowed checks:** `tests/sim/*_test.gd` open a window and need a GPU (`tools/run_sim_tests.sh` runs them one after another through `tools/run_windowed.sh` (which holds a lock so only one GPU run happens at a time), with a timeout each; helpers `sim_harness.gd`, `scenario.gd`, `smoke.gd`). `goldens_test.gd` compares `validate_dynamics.gd gpu <scenario> 1 6` with `tools/gpu/golden/dynamics_pooled_<scenario>_seed1_6h.txt`, byte for byte after a refactor that changes no behaviour; the goldens were made on Apple Silicon with Metal (a run is deterministic per seed on one machine, but another GPU or driver gives different numbers, so make a golden yourself there, before the change). The ad hoc checks are in `tools/gpu/` (`pool_*_check.gd`, `core_check.gd`, `view_check.gd`, `game_check.gd`...; not exported; run `godot --path . --rendering-driver metal --position 6000,6000 -s tools/gpu/<script>.gd -- <args>`, output to a file). Nothing else may use the GPU during timings.
- **Dispatching by the live count is not built (measured on the single-dish kernels, M1 Pro).** Its kernels ran over every slot, each returning past the count, at about 0.1 ms a step per 100,000 empty slots. An indirect dispatch (`compute_list_dispatch_indirect`) **does not see a kernel's write made earlier in the same submit**, but does see a `buffer_copy` between two lists, and a copy per step needs a new compute list per step, which cost 60-85 µs a step: the net was zero at a 106,000 limit and a loss at a full dish. The pooled kernels have not been measured this way.
- The release workflow runs `--import || true`, which hides a shader that fails to import, so it then runs `tests/gpu_shaders_test.gd` and stops the release if that fails.

## Running things

Tests are headless scripts: `godot --headless --path . -s tests/<name>.gd` (`dialog_test` is a scene: `godot --headless --path . res://tests/dialog_test.tscn`); each prints an OK line or the failures. Run `godot --headless --path . --import` after adding a `class_name` script or a new asset.

- After any interface change run `ui_lint_test`, `strings_test`, `fonts_test`, `screens_test`, `settings_test`, `toolbar_test`, `free_mode_test`, `tutorial_test` and `debug_log_test`.
- The simulation tests are slow and windowed (`tests/sim/`, see above) apart from `motion_table_test`. **Work out what the answer should be first, from sources or derivation, and use a test to confirm it once.** Do not run tests in a loop to discover what is correct: write down the expected number and why, and size the sample so it can tell the effect from noise.
- Outcomes are deterministic for a seed (identical on any thread count); only timing varies. Timings are noisy on a busy machine, so compare variants in the same sitting.
- Windowed runs (for screenshots) should be short, self-quitting and off-screen (`--position 6000,6000`). The game manages its own window (full screen, or the project's maximized mode) unless it is headless, run from a script (`-s`) or given `--windowed` or `--resolution` (`UserSettings._window_is_managed`); a game started from the editor is managed, so the editor's `--position` does not leave it small. A window that is not managed is kept as it was started for the run's first 10 s (`UserSettings.hold_windowed`, asked each frame by `PreferencesHook`): a window manager that lays windows out may resize a new one just after it opens, and a run measured in a window of another size, or with the pointer over the dish, is not the scene it claims (`tests/sim/interface_gate.gd` fails such a run). `--position 6000,6000` is off-screen only on a desktop that reaches that far: on a smaller one the system moves the window to a corner, partly in view. Never kill processes broadly. Delete temporary test files afterwards.
- **Native code** is `LineageStore` only: rebuild with `cd native && scons platform=macos arch=universal target=template_debug api_version=4.5 -j8` (and `template_release`; `native/godot-cpp` must be a clone at `GODOT_CPP_COMMIT` of `.github/workflows/build-native.yml`), and say when the C++ changed, since the other platforms' libraries come from the release workflow. Do not rebuild while headless runs that load the library are in progress.
- **The motion table** (`scripts/motion_table.gd`) is generated by `tools/gen_motion_table.gd` (about 5 minutes) and guarded by hashes: when `motion_table_test` says it is stale, regenerate it. A new constant in `SimConstants.build()` must be classified in `MOTION_INPUTS` or `OTHER_CONSTANTS`.

## Gotchas

- GDScript: `%g` is not a supported format; comparing a `String` to a `bool` with `==` is an error (check `is bool` first).
- The editor re-saves scenes and the theme in its own format (`&"Label"`); keep lint patterns tolerant of both. Typed node exports in a `.tscn` need `node_paths=PackedStringArray("prop")`. `.uid` files are tracked.
- Raw files (`.cfg`, `.txt`) are only exported when a preset's `include_filter` names them. The macOS export needs ETC2/ASTC import on (`project.godot`) and is ad-hoc signed, not notarized. A release is made by pushing a `v*` tag (see CONTRIBUTING.md).
- The tutorial runs on every goal-mode start and only when switched on in free mode; nothing about it is saved in goal mode.
- The medium is 25x thicker than water (`Biology.MEDIUM_THICKNESS`): a stopgap so plankton clouds last long enough to climb, not a realism choice. The nutrient grid has cells 2R/100 across, so a big dish keeps plankton as sub-grid Gaussian "clouds" until they have spread to about a cell.
