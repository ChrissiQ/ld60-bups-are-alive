# Instructions for coding agents

Bups Are Alive is a realistic bacteria-evolution simulation and game: Godot 4.7 with GDScript for the game, and a C++ GDExtension for the simulation. [README.md](README.md) says how to build and run it, and [CONTRIBUTING.md](CONTRIBUTING.md) what a good change looks like. This file is what an agent needs to know about the project before changing it.

## What the project is for

It is a laboratory for watching real evolution happen: bups eat, swim toward food, divide, mutate and compete at real scales (micrometres, seconds), and the player can run it from real time up to x10,000. When goals conflict, in this order:

1. **It must be watchable and fun at speed.** The top playback speed (x10,000) is the most important performance target. Anything that adds per-step cost needs its cost measured at that speed. A little speed can be traded for clear accuracy, not a large chunk.
2. **It models real evolution accurately.** It is a realistic *life* simulator, not just an E. coli simulator: prefer the realistic mechanism over a gamey one, and say where realism was scaled for playability (mutation *rates* are raised well above a real microbe's, the *shape* of the spectrum stays realistic). A feature borrowed from another organism is fine if the combined organism is plausible and keeps the feature's real costs and trade-offs.
3. Everything else.

There are exactly **two clocks**: real time, and the simulation clock (playback speed multiplies it). Do not invent a scaled "game clock"; show times with `SimClock.format`. Units are µm and seconds. "Metabolism" is a gene, nothing else.

## Layout

- `scripts/`, `scenes/`, `ui/`: the game. `scripts/dish.gd` owns a dish (drawing, picking, layers, plankton); `scripts/main.gd` is the game screen; `scripts/session.gd` carries state between screens; `scripts/start_conditions.gd` is how a dish begins; `scripts/goal_tracker.gd` holds the experiments' goals.
- `native/src/`: the C++ simulation. `BupSim` holds the bups, `NutrientField` the nutrient grid and the sub-grid plankton clouds, `params.h` the constants. `scripts/sim_constants.gd` builds the constants it receives.
- `text/strings.cfg`: every word the player reads. `text/names.txt`: random bup names.
- `tests/` and `tools/`: tests and generators. `gpu/`: the GPU path (see below). `.github/workflows/`: the native build and the release.

## Conventions the tests enforce

- **All player-facing text** lives in `text/strings.cfg`: `Strings.t("section.key", args)` in code, `"@section.key"` in scenes, a comment above each key. `tests/strings_test.gd` checks that every key exists and that every raw file the game reads is covered by each export preset's `include_filter` (a raw file missing from an export makes the game show keys instead of words).
- **UI styling lives in the theme** (`scenes/menu_theme.tres`). Use `theme_type_variation`; add a variation to the theme when none fits (its base type must be a plain Control type, not another variation). No per-node overrides, no styles or colours built in code (colours only in `dish.gd` and `genome.gd`), two typefaces in `fonts/` (Inter for text, Commit Mono for numbers; which is set only in the theme), numeric settings through `ui/setting_row.tscn`. `tests/ui_lint_test.gd` fails on any of this. Screen paths live in `scripts/scenes.gd`.
- A bup's name has one source (`bup_names.gd`); do not build names elsewhere.

## Repository conventions

- **A yes/no setting is a `ToggleRow`** (`ui/toggle_row.tscn`: its name, On and Off buttons, and what it does written below, always in view), never a bare toggle button and never explanation that only a hover shows (tooltips do not wrap and run off the screen: keep them short, for names and icons). Render a new screen (a `SubViewport` holding it, saved as an image) and look at it before calling it done.
- **Free-mode defaults are goal mode's settings.** `StartConditions.new()` holds the defaults, goal mode's dish is `dish.strike(null)`, which uses `StartConditions.new()` (`tests/free_mode_test.gd` checks the defaults), so free mode differs only in letting them be changed. A feature that is on in goal mode and a toggle in free mode is on by default there, and "reset to defaults" restores `StartConditions.new()`'s value.
- **The encyclopedia is kept true and complete, and kept to concepts.** An entry explains a term in up to two parts, kept apart as the Civilopedia keeps them: `<id>_about`, what it is in real life, and `<id>_game`, how it works in the game (values, ranges, costs, and where the game departs from real life: a rate raised, a trait standing for many genes, a number that is a game choice). It never says what to click or press, never what a control does: that is the tutorial's (`[tutorial]`, the steps in `Main._start_tutorial`) and the tooltips', which are names and icons only. Every change that alters what an entry says (a constant, a cost, a rate, how a gene or mechanism works, a name, a range) updates the entry in the same change, and a new gene, flag, mechanic, thing in the dish or term the player meets gets an entry (`scripts/encyclopedia.gd`, `[encyclopedia]` in `text/strings.cfg`); a changed or new interface part updates or adds a tutorial step. Check the game part against the code, not from memory. Anything about real biology is looked up and checked against sources before it is written: no misconception may stand in an educational text. `tests/encyclopedia_test.gd` checks the links, that every gene has an entry and that no entry tells the player what to click; it cannot check the facts.
- **Commit messages** are one short line in the present tense, third person ("Fixes source selection"), with no body and no attribution trailer.
- **Secrets:** do not create, edit or delete `.env` files; reference their variables.
- **Saves are not stable.** The game is unreleased, so do not write code that reads old save formats, and do not edit a real `save.json` or `free_settings.json` in the user data folder; tests use scratch paths.
- **Releases** are made by pushing a `v*` tag (see CONTRIBUTING.md); changing a workflow in `.github/workflows/` changes what builds.

## Interface design

The look and layout are one system. The theme (`scenes/menu_theme.tres`) is **generated** by `tools/gen_theme.py` from design tokens: edit the tokens or a variation there, run `python3 tools/gen_theme.py` from the project root, then `godot --headless --path . --import`; never edit the `.tres` by hand. Layouts are containers, never hand-placed offsets.

- **Tokens:** neutral dark panels (one fill, a hairline border, radius 10), one accent (teal-green) for selection and the primary action, amber only for goals and names, a coral of its own for warnings (`Warning`, `WarningIcon`), red only for danger; off-white text with muted secondary text, units smallest (`Unit`). Spacing 4 / 8 / 16 / 24 / 28 (`SnugStack`, `TightStack`, `RoomyStack`, `SpaciousStack`, `SectionStack`; rows `TightRow`, `TightGroup`, `SpaciousRow`, `SegmentRow`). IBM Plex Sans for text (Light 300 for long text and big type, Regular 400 for buttons and labels, Medium 500 only for the warning, Bold 700 only for the title screen's game name) and Commit Mono for every number (stat values, units, the graph, the readouts, figures inside text via `[code]`). Related things sit tight, unrelated groups clearly apart; text in a column shares one left edge (spacing goes outside text, never inside it).
- **Controls:** a yes/no setting is a `ToggleRow` (segmented On / Off; with `auto_text` a checkbox that dims the switch while the machine decides). Pages of one panel are tabs (`TabButton` in `Segments`); steps of a flow are a `StepIndicator`; a section that hides detail is a header button with a chevron (`SectionButton`); numbers are `SettingRow`; a secondary action is `SmallButton`, a real raised button (never a borderless "ghost" button or a bare text link: an action always looks like a button; Reset sits at the left of the footer, Back / Next at the right). Keys are shown in tooltips and the controls list, never in a button's or hint's text. A warning is the coral icon (`WarningIcon`) and text (`Warning`) together. Do not use a toolbar button for a setting, and do not make something that is not a control look like one.
- **Dialogs** (`scripts/dialog_style.gd`): no cross; the title and the text start at the same left edge, 24 px padding, buttons right-aligned and as wide as their words; OK is the main button, or, with the dialog's `destructive` meta, the cancel button is the main one and OK the outlined danger button.
- **In-game screen:** `HUD/Frame/Layout`: the top bar (readout, dish tabs that scroll (each with a small live picture of its dish), layer toggles, playback, menu), then the middle (tool rail and stage; the right-hand tray). The dish is framed in `%Stage` (`_fit_camera`, again whenever the stage resizes). **Everything that is a panel lives in the tray**, which scrolls when short: the goal, one card in the dish slot (the dish card with its collapsible "Dish details", or what is picked), then accordion sections (`TraySection`, `ui/tray_section.gd`: a `SectionButton` heading with a chevron at its right, content under it, put as the node's children in the scene): **Graph** (Y opens and closes it; a dish switch when there are several dishes, the time span switch, the trait drop-down, the plot), **All dish details** (the dishes running, the bups in all of them and the traits averaged over every bup of every dish), the watch list, and the **Freezer**. Add a new panel as a `TraySection`, not as a card of its own. What the pointer rests on is the hover card by the pointer and never moves the tray. `_adapt_layout` sizes the tray and the graph; the top bar drops its layer toggles on small windows. Every layout-only container has `mouse_filter` ignore or it swallows clicks meant for the dish.
- **The encyclopedia and tooltips:** what the game's terms mean lives in the encyclopedia (`scripts/encyclopedia.gd` for the order, `[encyclopedia]` in `text/strings.cfg` for every word, `ui/encyclopedia_panel.gd`), reached from the title screen and the pause menu, and opened on an entry by a click on a band of the genome map (`Main._open_encyclopedia`); an article links to another with `[url=id]words[/url]`, and `tests/encyclopedia_test.gd` checks every link. A new term gets an entry, not a long tooltip (tooltips are names and icons only), and the `TooltipFit` autoload wraps every tooltip to `UiText.TOOLTIP_WIDTH` characters a line as the pointer reaches its control.
- **The freezer:** a dish is frozen with the Freezer section's button ("Freeze this dish": the one in the main view) or by answering a pipette's question (`_ask_about_old_dish`: after the pipette makes its new dish the game holds and a dialog asks Keep, Freeze or Trash for the dish the bups came from; only a button answers; play, which the pipette timer was holding, goes on after). `Main.freeze_dish` keeps `Dish.to_dict()` (the save format, so no C++ or kernel change) with its number, its bup count and its picture, and frees the dish (`_remove_dish`): a frozen dish is in no running list, so it is outside the world's clock, Auto's load and the all-dishes graph, and does not advance. `Main.thaw` makes a new dish under the old number (`add_dish(null, number)`, `Dish.from_dict`) at the world's time: `_move_saved_dish_to` moves the plankton's and the bloom's times on by the time away and levels the history over it (the frozen time is not simulated, and bups have no age to correct). `trash_dish` removes a dish for good. The last running dish can be neither frozen nor trashed; at `MAX_DISHES` running a dish cannot be thawed (frozen ones do not count). When the last running dish dies out with dishes frozen the game does not end: it stays, empty, until one is unfrozen. The freezer is not saved with a game (several dishes are not either). `tests/freezer_test.gd`.
- **The genome map:** a bup's genes are shown as a chromosome (`ui/genome_ribbon.gd`, `ui/genome_slot.gd`), the way a graphical genotype colours one: a bup is haploid with one chromosome, so the loci are bands down one bar in the fixed order `Genome.LOCI` (the donor's F factor, then speed, sense, metabolism, size in the order a donor transfers them, then the mutator and the acetate key), each band its locus's colour (`Genome.LOCUS_COLORS`) with the gene's symbol in it, its shade the allele (dim to bright across the gene's range), the name, the value and an arrow where it differs from the founders' beside it. A bup without the F factor has an empty band there. A dead bup's family record keeps no F factor, key or raised ceilings, so those bands are grey with a "-". A new gene or flag goes in `Genome.LOCI`, the ribbon's `show_bup`, and the `[genome]` strings.
- Bups are artwork, not interface: accessibility work is for the interface (contrast, reduced motion, sizes); never alter bup colours or behaviour for it.
- Look at a screen at 100%, 150% and 250% in a busy state (several dishes, a picked bup, a full watch list, a tool open) before calling it done, and run the full interface suite as tracked tasks (a script error leaves a headless test hanging until its timeout).

## Interface size

The window is not stretched (`window/stretch/mode="disabled"`): at 100% the interface is the size an ordinary desktop program has on the display (`UserSettings.native_scale()`, the display's density). The player's setting (`UserSettings`, 60-250%, Options) grows the text all the way but the room round it (paddings, gaps, the height of buttons and rows) only to the power `ROOM_EXPONENT`: the window's content scale carries the room, and `UserSettings` rewrites the project theme's font sizes for the rest of the text, so bigger text never means all-the-way bigger buttons and panels. Consequences for layout: never place a panel at a fixed pixel offset that a bigger font can overrun (use containers, a title's measured bottom, a ScrollContainer as the fallback), and look at a screen at 100%, 150% and 250% before calling it done (a capture script can set `UserSettings.native_override` and `ui_scale`, then `apply()`). Headless runs are given a 1280 x 720 window and ignore the saved preferences.

## Debug log

F12, on any screen (undocumented in the game: not on the HUD or in the controls; only its notice is in `strings.cfg`), writes `bups-<date>_<time>-<ms>.log` and a `.png` of the screen to `user://logs/` (on macOS `~/Library/Application Support/Godot/app_userdata/<project>/logs/`), then shows "Debug info logged" for a few seconds. The log is JSON: the run's settings and state, the mean nutrient by distance from the dish centre (a rim ring or step shows there), the selected bup, and every simulation constant. It works in menus and in the tutorial: the `DebugHotkey` autoload (`ui/debug_hotkey.tscn`) takes the key, logs the current screen and the session, and the screen's `dish` and `debug_state()` when it has them. Each write prunes the folder to the newest 20 logs and nothing older than 14 days. When diagnosing a report, read the newest log (`ls -t`) and its screenshot. `scripts/debug_log.gd` builds it; add to `report` what a diagnosis keeps needing, and keep personal data out.

## GPU path

The whole simulation step can also run on the GPU (compute shaders through `RenderingDevice`), as the fast path for big populations. `gpu/kernels.gd` (`GpuKernels`) holds every kernel as GLSL text and its buffer list; `tools/gen_gpu_shaders.gd` writes them to `gpu/shaders/<kernel>.glsl` (generated: edit `kernels.gd`, never the `.glsl`); `gpu/gpu_sim.gd` (`GpuSim`) loads the imported shaders and runs them. `GpuSim.new(null, true)` compiles the text from `kernels.gd` at run time instead (for tools).

- After editing `gpu/kernels.gd`: `godot --headless --path . -s tools/gen_gpu_shaders.gd`, then `godot --headless --path . --import` (the importer reports success even when a shader fails to compile; `tests/gpu_shaders_test.gd` reads the errors and fails on stale files).
- **A death gives back nutrient:** a bup that starves or dies by chance returns `Biology.DEATH_RELEASE` of its body (mass at `COST_PER_MASS`) as a cloud where it died; one displaced at the limit (the CPU's Moran replacement, the GPU's trim) or removed by an edit returns nothing. On the GPU it is `death_clouds`/`death_count` after `finalize` (slot per dead bup, empty for a trimmed one); the cloud kernels run whenever it is on. With the advanced option `death_husks` (`Dish.death_husks`, off by default) a death leaves a husk instead (`BupSim.husks`, `Biology.HUSK_SECONDS`): the husks are the CPU's on both backends, the GPU's deaths reach it in the death events (words 5-7: x, y, the energy), and the GPU makes no cloud for them (`death_puff` 0 in the batch's plan).
- **Starvation (stationary phase):** `Dish.stationary_phase` (`StartConditions.stationary_phase`, on by default in free mode, an advanced option; goal mode's dish never has it) changes what happens to a bup whose reserve is at `MAINTENANCE_FLOOR`: it stops growing, pays `Biology.STARVE_MAINTENANCE` from its reserve and then from its mass (it shrinks), and dies at a constant rate that grows with its metabolism gene (`Biology.STARVE_DEATH_RATE`, `STARVE_DEATH_GROWTH_HOURS`) or when it has shrunk to `STARVE_MIN_MASS_SHARE` of its birth mass, instead of dying when the reserve is gone. CPU: `pay_upkeep_and_grow` and `starved_to_death`; GPU: the end of `swim` and `life` (P[85] from the batch's plan).
- **Conjugation:** a bup's record word 14 is its donor flag (0 or 1; the drag cost is worked out from the speed gene). A donor (`Genome.DONOR_*`, `CONJ_*`) copies a run of its genes into a non-donor it touches: CPU `BupSim::conjugate` (every donor against every bup), GPU `conj_clear`/`conj_insert`/`conj_apply` before `life` (a hashed table of donors by 20 µm cell, each recipient looks at its 3 x 3 cells and changes only itself). `tools/gpu/validate_conjugation.gd` compares them.
- **Raised ceilings:** a bup's record word 12 is its `reach` (two bits a gene, speed the lowest: how many times that gene's ceiling has been raised, `Genome.REACH_*`), not its food yield, which is `exp(-harm) / sqrt(metabolism)` worked out where it is read (the CPU keeps it in `Bup.yield`). A raise multiplies the gene's `gene_max` in the mutation clamp (`BupSim::gene_ceiling`, and `life`), costs growth, and travels with the genes in a conjugation.
- **Acetate (the second food):** a bup that takes in more than its growth can use lets go of acetate besides (`Biology.ACETATE_*`: threshold-linear in the growth rate its intake could sustain, its own gain not reduced), and a bup with room in its reserve takes acetate up from the cell it is in, at up to 0.45 of its glucose rate and less while there is glucose. The acetate is a second `NutrientField` in `BupSim` (`acetate`: the main field's grid and medium, no clouds, diffused with it; saved as `acetate`). CPU: `acetate_share` and `take_acetate` in `BupSim::step`'s serial loop. GPU: the end of `apply` (excretion, and the want), then `ac_cells` and `ac_apply` (`CONC2`, `WANT2`, `CELL2`, sums in `AWLO`/`ADLO`...), `diffuse2_a`/`diffuse2_b`, P[101-103]; `GpuWorld` carries it across a switch (`GpuSim.acetate` before `load_state`). Not modelled: inhibition by acetate (not significant at neutral pH), the glucose of clouds in the repression, a view of it in the game. `tools/gpu/acetate_check.gd` checks the switch; `game_dynamics.gd` prints an ACETATE line per hour for `compare_dynamics.py`.
- **Several dishes (M1):** `main.gd` keeps `dishes` (every running `Dish`, all children of Main at `DISH_SPACING` µm apart in the one world) and `dish`, the one in the main view; `add_dish(start)` joins one, `set_main_dish(d)` brings it into view (graph, watch list, layers, camera follow; a selection or lineage open on the old one is closed). Every dish advances to one shared world clock (`_advance_world`: the target is a frame of simulated seconds past the slowest dish, so no dish runs faster than another; if the machine cannot keep up the whole world slows together). A dish is advanced **once a frame** (a second, small request in the same frame cuts the GPU's steps for the frame to one: `GpuWorld.steps_for` keeps its budget against the most steps asked lately, `_wanted_ref`, not against one frame's request). When the dishes are further apart than a frame holds (slowing down from a fast speed leaves one a minute ahead), `_advance_world` lets the ones behind catch up first (`CATCHUP_SECONDS` a frame, what the budget allows) instead of the ones ahead standing still for the gap. Auto weighs the processor's whole load (`Dish.other_cpu_load`: the cost model's estimate for the other dishes still on it) and one dish at a time changes backend (`_let_one_dish_switch`). `ui/dish_strip.gd` (`DishStrip`) shows a live thumbnail of each (a `SubViewport` on the same `World2D` with its own camera, redrawn once a second) and is hidden with one dish. A dish that dies out pauses the game on it (`_on_dish_extinct`); resuming deletes it (`_retire_extinct`: the dish before it, or the next, comes into view, and dish numbers are never reused); the last dish dying out ends the game (`_game_over`, `EndDialog`: start again or quit to the menu, nothing else resumes). Goal mode stays single (the pipette is locked there). `tests/dishes_test.gd`, `tools/gpu/dishes_check.gd`, `tools/gpu/dishes_perf.gd`.
- **Acetate key:** `Genome.key_level(reach)` (bits 8-9 of the `reach` word: 0 none, 1 potentiated, 2 the key; `reach_levels` and the gene-ceiling code read only the low eight): a division potentiates a level-0 line at `KEY_POTENTIATION_RATE`, a level-1 line makes the key at `KEY_RATE`; the key multiplies acetate uptake by `KEY_FACTOR` (P[106], `take_acetate`, the end of `apply`) and costs `KEY_COST` of growth (P[107]). The stats pass sums it as a ninth value (`key`, a graph series). `tools/gpu/validate_key.gd` and `validate_mutation.gd` (args 4-6) compare the backends.
- **Pipette and plankton husks:** `Main.pipette(world, radius)` takes the bups in a circle (`BupSim::take_disc`, the main dish is brought to the CPU) into a new dish (`add_state_bytes` with `keep_ids`: the same bups, same ids; their whole family tree comes by `lineage_export_bytes` / `lineage_import_bytes`; `Dish.moved_out`, `founded_from` feed the panel lines). The watch list is one for all dishes (`WatchPanel.dishes`), what the layer buttons show is one choice for every dish, and each dish keeps the zoom and position the camera had when it was last looked at (`Dish.view_zoom`) and, with the timer on (`tool_options.pipette_timer_changed`), the game pauses every so many simulated hours until a pipette moves bups (`Toolbar.resume_locked`). `Dish.plankton_husks` (`StartConditions.plankton_husks`, an advanced option) makes a dying plankton leave a husk (`BupSim::add_plankton_husk`) instead of a cloud; dead-bup husks have their own switch (`BupSim::set_death_husks`). Husks are drawn with the nutrient layer (`Dish._draw_husks`, at most `HUSK_DRAWN_MAX`) and inspectable like everything else in a dish: the select tool's Husks mode (and Inspect all) finds one by its place (`BupSim::husk_near`, `Dish.husk_at`, `husk_details`; a husk has no id), with a hover card, a pinned panel and a ring. Changing `BupSim::husk_near` or the husk export format is a native change.
- **Divisions and generation:** a bup has `divisions` (record word 20), the divisions in its line: a division adds one to the parent, lethal daughter or not, and the daughter starts at the parent's new count, as both products of a fission are one step further on. A bup has no generation of its own. The population's `generation` is the mean `divisions` of the bups alive in the dish (`population_stats`'s "generation", the stats pass's tenth sum on the GPU), as the LTEE counts generations per population; a pipette keeps the bups' counts, so the new dish carries on the count of its source.
- **Cost of a nearly empty dish (processor):** measured with a symbol build (`debug_symbols=yes`, `xcrun atos` on `sample` output), the clouds' lookup lists (`NutrientField::rebuild_hash`) were the cost, not the grid: they are cut into bins of `BIN_CELLS` (2) cells (the bin size changes the work, not what a read finds or the order it sums in, so results are identical), `snapshot(readers)` makes nothing for a step with no bups, and `diffuse` skips a field with nothing in it (the second food mostly is). A hash of a seeded CPU dish (population statistics, field values, cloud count) is the same before and after; `export_state_bytes` is not a usable hash (it differs run to run with either library).
- **Both backends:** every model change must land in the C++ and in the GPU kernels. The CPU path stays fully maintained (web builds have no compute).
- The drawing's kernels are in `gpu/kernels_draw.gd` (`GpuKernels.all()` includes them); `gpu/gpu_world.gd` (`GpuWorld`) is the game's side of the GPU path, and `scripts/dish.gd` sends every question about the bups to it while `gpu_active` (the branches and the `_advance_gpu`, `_draw_bups_gpu`, `_choose_backend`, `_to_cpu_for_edit`, `_mark_gpu_dirty` hooks). A bup record is 24 words with its 64-bit id as two uint words (0 and 21; word 13 is the bup's `mutator`, its mutation rate as a multiple of the usual, and the building size is worked out from the size gene; layout at the top of `gpu/kernels.gd`, the same as `BupSim.export_state_bytes`): move records through the integer views (`BUPS_V4U`...), never as floats. `tests/gpu_native_test.gd` checks the native calls the GPU path uses.
- The windowed checks live in `tools/gpu/` (not run by the headless suite; `tools/*` is not exported): `godot --path . --rendering-driver metal --position 6000,6000 -s tools/gpu/<script>.gd -- <args>`, output to a file. `validate_dynamics.gd gpu <scenario> 1 6` must reproduce `tools/gpu/golden/` byte for byte after a refactor that changes no behaviour (the goldens were made on Apple Silicon with Metal: a run is deterministic per seed on one machine, but another GPU or driver gives different numbers, so compare against a golden you made yourself there, before the change; `GPU_FROM_SOURCE=1` compiles from source). `game_check.gd` drives a real `Dish` as `main.gd` does and checks every backend switch as it happens (modes `smoke`, `auto`, `edits`, `flap`, `long`, `perf`, `frame`, `thresholds`; see its header); `switch_check.gd`, `events_check.gd`, `queries_check.gd`, `draw_check.gd` check the parts; `cap_check.gd` checks that the population holds at the bup limit (on the GPU the trim expects the step's growth plus a margin of `CAP_SIGMAS` standard deviations, so the count stops a little short of the limit, about 0.1% below it at 300,000, and is over it in under 1% of frames). Nothing else may use the GPU during timings.
- **Dispatching by the live count was measured and not built.** The step's kernels run over every slot (the limit plus 5%), each returning at `i >= CNT[0]`, which costs about 0.1 ms a step per 100,000 empty slots (1,000 bups: 450 µs at a 1,000 limit, 540 at 106,000, 635 at 300,000; a dish at its limit gains nothing). The count lives on the device and changes every step, so the sizes must come from it: an indirect dispatch (`compute_list_dispatch_indirect`, buffer made with `STORAGE_BUFFER_USAGE_DISPATCH_INDIRECT`) **does not see a kernel's write made earlier in the same submit** (it reads what the buffer held when the submit began, in one compute list or two), but does see a `buffer_copy` between two lists (or a submit and sync, which the main device cannot make). A copy per step needs a new compute list per step, which cost 60-85 µs a step (a fixed ~250 µs besides for the first split of a batch): the net was zero at a 106,000 limit and a loss at a full dish. A bound from the host's last count would drop births when growth outruns it. Revisit only if the limit becomes much larger than the usual populations.
- **Cost of a nearly empty CPU dish, measured after the lookup-list fix** (50 bups at x10,000 in 83 s frames, `Dish.advance`): 45 mm, 568 clouds: x68,000 (1.2 ms a frame); 90 mm, 6,130 clouds: x46,000 (1.8 ms); the same dishes with few clouds 1.1 ms. The clouds are at most 0.7 ms of a frame (1-8% of the budget at 120 Hz), so skipping the clouds far from the bups (and keeping them for the hover card, the debug rings, the GPU's field export and the drawing) was not built.
- **A dispatch runs whole workgroups.** A kernel dispatched for fewer threads than its `local_size_x` (one thread runs a group of 64 invocations) must bound its index: a single-thread kernel begins with `if (gl_GlobalInvocationID.x != 0u) return;`, the others return past their count. Without it a second SIMD group sometimes applied an update again under GPU load (doubled deposits and clouds, the step counter and next id advanced twice).
- **The main RenderingDevice** (the game's GPU path runs on it, so the bups are drawn from its buffers): every call goes through `RenderingServer.call_on_render_thread`; never `submit()` or `sync()` (the frame submits); results come back with `buffer_get_data_async` a few frames later (the stalling `buffer_get_data` only where a stall is meant: a switch of backend, a save, an edit); every `buffer_update` of a batch comes before its `compute_list_begin` (the device refuses updates while a compute list is open); never set `multimesh.buffer` or a per-instance setter on the GPU-drawn MultiMesh (a CPU copy would overwrite the GPU's).
- **The backend setting** is `StartConditions.sim_backend` (`auto`, `cpu`, `gpu`: free setup's Advanced options; goal mode is always Auto), changed while a dish runs with `Dish.set_backend_setting`. `Dish._choose_backend` asks it again at every `advance`: steps of `FINE_STEP` or less always run on the CPU (the GPU has no fine path; fine or coarse is judged by `Dish.rule_step` on the playback speed over the usual frame, so one stray short frame at x100 does not hand back to the CPU), the GPU takes over after `COARSE_FRAMES_TO_GPU` coarse frames, Auto weighs the cost model (`CPU_STEP_MODEL`, `GPU_STEP_MODEL`, `GPU_FRAME_USEC`, per 60 Hz frame) and hands back after `AUTO_DOWN_FRAMES` frames. The pause menu's record and the debug log say which backend runs.
- The release workflow runs `--import || true`, which hides a shader that fails to import, so it then runs `tests/gpu_shaders_test.gd` and stops the release if that fails.

## Running things

Tests are headless scripts: `godot --headless --path . -s tests/<name>.gd` (`dialog_test` is a scene: `godot --headless --path . res://tests/dialog_test.tscn`); each prints an OK line or the failures. Run `godot --headless --path . --import` after adding a `class_name` script or a new asset.

- After any interface change run `ui_lint_test`, `strings_test`, `fonts_test`, `screens_test`, `settings_test`, `toolbar_test`, `free_mode_test`, `tutorial_test` and `debug_log_test`.
- The simulation tests are slow (`model_test`, `substep_test`, `cloud_test`, `motion_table_test`, `smoke`). **Work out what the answer should be first, from sources or derivation, and use a test to confirm it once.** Do not run tests in a loop to discover what is correct: write down the expected number and why, and size the sample so it can tell the effect from noise.
- Outcomes are deterministic for a seed (identical on any thread count); only timing varies. Timings are noisy on a busy machine, so compare variants in the same sitting.
- Windowed runs (for screenshots) should be short, self-quitting and off-screen (`--position 6000,6000`). The game manages its own window (full screen, or the project's maximized mode) unless it is headless, run from a script (`-s`) or given `--windowed` or `--resolution` (`UserSettings._window_is_managed`); a game started from the editor is managed, so the editor's `--position` does not leave it small. Never kill processes broadly. Delete temporary test files afterwards.
- **Native code:** rebuild with `cd native && scons platform=<macos|windows|linux> arch=<universal|x86_64> target=template_debug api_version=4.5 -j8` (and `template_release`), and say when the C++ changed, since the other platforms' libraries come from the release workflow. Do not rebuild while headless runs that load the library are in progress.
- **The motion table** (`scripts/motion_table.gd`) is generated by `tools/gen_motion_table.gd` (about 5 minutes) and guarded by hashes: when `motion_table_test` says it is stale, regenerate it. A new constant in `SimConstants.build()` must be classified in `MOTION_INPUTS` or `OTHER_CONSTANTS`.

## Gotchas

- GDScript: `%g` is not a supported format; comparing a `String` to a `bool` with `==` is an error (check `is bool` first).
- The editor re-saves scenes and the theme in its own format (`&"Label"`); keep lint patterns tolerant of both. Typed node exports in a `.tscn` need `node_paths=PackedStringArray("prop")`. `.uid` files are tracked.
- Raw files (`.cfg`, `.txt`) are only exported when a preset's `include_filter` names them. The macOS export needs ETC2/ASTC import on (`project.godot`) and is ad-hoc signed, not notarized. A release is made by pushing a `v*` tag (see CONTRIBUTING.md).
- The tutorial runs on every goal-mode start and only when switched on in free mode; nothing about it is saved in goal mode.
- The medium is 25x thicker than water (`Biology.MEDIUM_THICKNESS`): a stopgap so plankton clouds last long enough to climb, not a realism choice. The nutrient grid has cells 2R/100 across, so a big dish keeps plankton as sub-grid Gaussian "clouds" until they have spread to about a cell.
